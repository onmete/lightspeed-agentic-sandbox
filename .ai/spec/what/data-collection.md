# Agentic Data Collection

The sandbox exports a faithful representation of the GenAI v1.41 conversation it observes at provider/tool boundaries through ordinary correlated OTLP **trace spans**, not custom `gen_ai.*` span events or an OTLP Logs product signal. The approved design `docs/superpowers/specs/2026-09-24-sandbox-genai-transcript-design.md` supersedes the earlier `gen_ai.input`, `gen_ai.choice`, `gen_ai.tool.call`, `gen_ai.tool.result`, `gen_ai.output`, and synthetic `gen_ai.skill.*` event proposal. The workspace parent `ols/.ai/spec/what/agentic-data-collection.md` owns cross-repository collection and reconstruction semantics; this spec owns sandbox production only.

## Producer boundary and correlation

1. When the shared trace runtime is recording, the sandbox MUST record available full content on standard GenAI spans and export those spans without modification if `OTEL_EXPORTER_OTLP_ENDPOINT` is configured. With no endpoint, no OTLP product trace is exported; audit-enabled stdout remains a separate compliance destination. No separate product endpoint, file, custom event stream or GenAI OTLP Logs product copy is introduced. `LIGHTSPEED_AUDIT_ENABLED` and `LIGHTSPEED_CAPTURE_CONTENT` govern only separate compliance views and MUST NOT suppress or change recorded source-span content.
2. A valid operator `TRACEPARENT` MUST parent one sandbox `invoke_agent lightspeed` INTERNAL span; when absent or invalid the sandbox starts a new trace. Each genuine SDK model call MUST have its own `chat {model}` CLIENT child, and each tool actually executed locally MUST have an `execute_tool {name}` INTERNAL sibling. These sandbox spans MUST carry literal `agenticrun.uid` and `agenticrun.phase` when supplied by the batch correlation configuration; missing values MUST NOT be invented or taken from resource attributes. Spans retain native start/end times, status, trace/span IDs and parent ID. Parallel tools MUST NOT be serialized artificially.
3. The agent span MUST record the effective initial user prompt including its formatted context prefix as one standard `gen_ai.input.messages` message and system instructions separately as `gen_ai.system_instructions` when supplied. Its `gen_ai.output.messages` MUST contain exactly the structured terminal `AgentResult.output` after post-processing, including a domain `success=false` result. A pre-terminal timeout, exception or absent usable provider result MUST have ERROR and a low-cardinality `error.type`, without terminal output. No exception text is copied into product spans. `finish_reason=stop` on completed agent output is an instrumentation-normalized agent-lifecycle fallback, not a provider claim.
4. Provider adapters MUST use their actual model-call boundary to observe ordered effective model input messages, output message choices, reasoning when exposed, tool definitions where actually offered, per-call observed usage and response model, and SDK finish reasons if available. A missing provider finish reason MUST use the documented schema-valid unknown sentinel only when necessary to serialize an observed output choice. Never invent unobserved model calls, hidden reasoning, response models, or token counts. Model and agent `gen_ai.output.type=json` is set when JSON output was requested.
5. Model output tool requests MUST use schema-valid `tool_call` parts with name, arguments and the observed or stable generated ID. Later model input tool responses MUST use `tool_call_response` parts with that same ID and the required `response` field. The matching executed tool span MUST use the same call ID, full structured arguments, and its complete tool-callback result. DeepAgents MUST defer the success result attribute until the corresponding effective model-visible result reaches the next model request; when inspection is enabled, this boundary follows successful inspection. The subsequent `chat` input records the exact effective, possibly transformed content. An inspection failure MUST end the pending tool span with ERROR and `error.type`, without a success-result attribute. Failed tool spans MUST have ERROR/`error.type` and no success-only result; a model-visible error response remains visible in the next model input if the SDK sent it. Middleware-rejected or server-side tool requests do not acquire invented local-execution spans.
6. Actual registered skill instructions MUST be represented only by the ordinary SDK tools that actually made them model-visible (Gemini's native `load_skill` or another adapter's real loader/read operation). The raw successful tool result and any SDK-trimmed next model input remain distinct, without duplicating skill content in a custom event. Mere skill registration, discovery, staging, or arbitrary `SKILL.md` reads MUST NOT create a synthetic skill-used event.

## Source fidelity and collection

Content-bearing span attributes `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, `gen_ai.tool.definitions`, `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result` use standard v1.41 message/object JSON strings on the Python span API. Preserve literal UTF-8 text, Unicode, payloads and ordered parts without telemetry-side redaction or silent truncation. Tool adapters may apply output bounds before callback observation—for example, DeepAgents LocalShellBackend caps command output at 4,000 bytes (`MAX_TOOL_RETURN_CHARS`); record exactly that observed result and the distinct later model-visible input when SDK shaping differs. No single run-wide `chat` span or choice-event buffering stands in for actual per-request operations.

The Collector mechanically classifies eligible sandbox `invoke_agent`/`chat` spans carrying input or output messages and `execute_tool` spans carrying arguments/result (or call ID plus error type) into Transcript candidates. It retains one raw envelope per content-bearing source span, rather than duplicating that span into Actions; metadata-only operations remain Actions. SQL may order non-overlapping operations by timestamps/topology, expand messages by index, and match tool IDs without claiming a total order over overlapping tools. The sandbox itself does not assess collection state or reconstruct downstream logical models.

See `audit-logging.md` for audit-gated stdout/templog projections, `provider-contract.md` for native adapter normalization, and `run-api.md` for batch trace and effective-input lifecycle.
